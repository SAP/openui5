Manual Integration Test: Create Inline

DESCRIPTION

Test the inline creation of new sales orders directly within a table row using an OData V4 binding with $auto update group and inactive context support. Verify that the server-assigned SalesOrderID and read-only defaults are reflected in the UI after a successful POST, and that toolbar filter and sort operations behave correctly. Also verify that an activation prevented by validation (empty Buyer) is not a dead end but can be resolved by entering a valid Buyer ID.

PREPARATION

To check console errors open the developer tools before starting the application and check with each step, that there are no errors and warnings.

Testing with mock data

Start the application: CreateInline
Note: The mock server responds almost instantly, so the transient (in-flight) row state during a POST is barely visible. To observe it during manual testing, append &autoRespondAfter=1000 (delay per mock response in milliseconds) to the URL: CreateInline (delayed mock responses)

REALIZE and CHECK

Scenario 1: Initial Load and Rendering

  1. Open the application URL from the Testing with mock data section above.
  2. Check: The table header shows 6 Sales Orders.
  3. Check: The table contains exactly six data rows with pre-filled Sales Order ID, Buyer, Currency, Gross Amount, Note and Status values. The Buyer column shows the buyer ID together with the buyer's company name (e.g. buyer ID 0100000000 with company name SAP). Gross Amount is read-only. Each of these rows has the state icon with the tooltip From Server (cloud icon).
  4. Check: The very first row is an empty inline creation row. Its state icon has the tooltip Inactive (minus icon). The Buyer and Note inputs are editable (enabled); the Currency cell is a plain text that displays the default EUR. The Sales Order ID, Gross Amount and Status cells are empty.
  5. Check: The action button at the end of the empty inline creation row is invisible (hidden); it becomes visible only once at least one field has been filled.
  6. Check: The six data rows each have an enabled delete (x) icon at the end of the row (tooltip Delete).

Scenario 2: Successful Inline Creation with $auto Submit

  1. Click into the Buyer input of the inline creation row at the top of the table.
  2. Enter the buyer ID 0100000000 into the Buyer input.
  3. Move focus out of the Buyer field (for example press Tab or click into the Note input of the same row). Leaving the Buyer field commits the entered value and triggers row activation, since the buyer is the only required field — the Currency is already pre-filled with EUR.
  4. Check: While the POST request is in flight, the state icon of the row shows the tooltip Transient (plus icon) and a blue marking is visible on the left side of the row. With the default mock server the response is almost instant, so this state only flashes by; use the autoRespondAfter URL parameter (see PREPARATION) to slow the mock responses down enough to observe it.
  5. Check: A new empty inline creation row with the Inactive (minus icon) tooltip appears directly below the just-activated row (as the second table row). The activated row (now Transient) stays at the very top: the first created row is placed at the top and every following one is appended to the end of the block of rows created in this session.
  6. Check: The table header count increases to 7 Sales Orders.
  7. Check: A MessageToast appears at the bottom of the screen with the text Sales Order 0500000006 created.
  8. Check: The state icon of the formerly transient row changes to the tooltip Persisted (checkmark icon). The blue marking on the left side of the row remains visible.
  9. Check: The Sales Order ID cell of that row now contains the auto-generated value 0500000006.
  10. Check: The Gross Amount cell of that row shows a default zero value (e.g. 0.00, depending on locale).
  11. Check: The Status cell of that row shows New.
  12. Check: The Buyer input of the persisted row becomes read-only (disabled), since the row has now been stored on the server, and it now also shows the buyer's company name (SAP) next to the buyer ID. The Note input of that row remains editable, while the Currency stays a plain text. The same applies to the rows fetched from the server: their Buyer is read-only while the Note stays editable. Only transient (not yet stored) rows keep an editable Buyer.
  13. Click into the Note input of the same row, enter Test inline create and press Enter or leave the field to commit the change.
  14. Check: The note is updated without error (a PATCH request is sent to persist the change).

Scenario 3: Validation — Empty Buyer Prevents Activation

Part A: Reset the prevented row via Delete

  1. Click into the Note input of the (still empty) inline creation row — after Scenario 2 it is the second row, directly below the sales order you just created — enter No buyer yet and move focus out of the field (for example press Tab or click another cell) to commit the value. Leave the Buyer field empty.
  2. Check: Committing the first field value immediately triggers an activation attempt. Because the Buyer is still empty, activation is prevented at once. An error indicator appears in the Buyer field of the row; move the focus into the Buyer field to see the error message Buyer ID must not be empty. The state icon remains Inactive (minus icon) and no POST request is sent.
  3. Check: A new empty inline creation row is nevertheless added below the current row, so the user can keep creating further entries. Starting to edit a row always spawns the next empty row, regardless of whether the current row can be activated.
  4. Check: A blue marking appears on the left side of the edited row and its action button becomes visible, showing the delete (x) icon (tooltip Delete).
  5. Check: The table header count does NOT increase — inactive rows (both the prevented row and the newly added empty one) are not counted until they are activated.
  6. (Optional) Change the Note text (for example to Missing buyer) and leave the field. The row still cannot be activated while the Buyer is empty, and the error remains.
  7. Click the delete (x) icon (tooltip Delete) at the end of the inline creation row to reset it.
  8. Check: The edited row is removed from the table, leaving only the single empty inline creation row. The error indicator disappears together with the removed row, and its validation message is removed from the message model.

Part B: Resolve the prevented activation by entering a Buyer ID

  1. Repeat the activation attempt from the previous part: click into the Note input of the empty inline creation row, enter Buyer to be added and move focus out of the field to commit it, again leaving the Buyer empty.
  2. Check: As before, activation is prevented — the Buyer field shows the error indicator (message Buyer ID must not be empty), the state icon stays Inactive (minus icon), the header count does NOT increase, and a new empty inline creation row is added below.
  3. Now click into the Buyer input of that same (prevented) row, enter the buyer ID 0100000001 and move focus out of the field to commit it.
  4. Check: The validation error is resolved — the error indicator disappears from the Buyer field and its message is removed from the message model. A new activation attempt is triggered, and this time it succeeds, so a POST request is sent: the state icon briefly shows Transient (plus icon) with the blue marking (use the autoRespondAfter URL parameter to observe it).
  5. Check: This second activation does NOT add another empty inline creation row — the empty row spawned in step 2 remains the single empty creation row. (Only the first activation of an inactive row spawns the next empty row.)
  6. Check: The row becomes Persisted (checkmark icon) and a MessageToast shows Sales Order 0500000007 created. The Sales Order ID cell shows 0500000007, Gross Amount shows a default 0.00, Status shows New, and the Buyer input becomes read-only and now shows the company name Becker Berlin next to the buyer ID. The table header count increases to 8 Sales Orders.
  7. Clean up (important): Click the delete (x) icon (tooltip Delete) at the end of the just-persisted row (0500000007) to remove it again. This restores the state for the following scenarios, so that the only sales order created in this session remains 0500000006.
  8. Check: The row is removed, the header count returns to 7 Sales Orders, and the single empty inline creation row is again directly below the sales order created earlier (0500000006) as the second row — the same state as before Part B (the created 0500000006 stays pinned at the top until the next sort or refresh). The subsequent scenarios (Sort, Filter, Refresh, Delete) operate on the same data as before.

Scenario 4: Toolbar Operations — Refresh, Sort and Filter

Refresh

  1. Press the Refresh button (refresh icon) in the toolbar.
  2. Check: The table reloads its data. The sales order created in this session (0500000006) remains visible, but moves from the top to its actual position at the end of the data rows (the top placement is only kept until the data is reloaded).
  3. Check: The empty inline creation row is still shown at the top after the data is received — the inactive row is kept across the refresh; no new creation row is generated.

Sort by Sales Order ID

  1. Press the sort button in the toolbar (tooltip Sort by Sales Order ID).
  2. Check: The sort button icon changes to the ascending sort icon. The data rows are reordered with the lowest Sales Order ID first (0500000000 at the top of the data rows).
  3. Check: Only the empty inline creation row (inactive) stays at the top of the table. The persisted sales order created in this session is sorted together with the other persisted rows from the server according to its Sales Order ID.
  4. Press the sort button again.
  5. Check: The sort button icon changes to the descending sort icon. The data rows are reordered with the highest Sales Order ID first. The sales order created earlier in this session (0500000006) is the highest and appears at the top of the data rows.
  6. Press the sort button a third time.
  7. Check: The sort button icon returns to the default unsorted icon. The rows return to their original server order.

Filter by Buyer ID

  1. Enter 0100000001 in the Filter by Buyer ID search field and press Enter or click the search icon.
  2. Check: Only rows whose Buyer ID equals 0100000001 are shown (two rows for the mock data: Sales Orders 0500000002 and 0500000005).
  3. Check: The empty inline creation row (inactive) is still visible at the top of the table. The sales order created earlier in this session is no longer shown, because its Buyer ID 0100000000 does not match the filter.
  4. Clear the search field and press Enter or click the search icon.
  5. Check: All data rows are shown again.

Scenario 5: Delete a Persisted Row

  1. Click the delete (x) icon (tooltip Delete) at the end of any persisted data row.
  2. Check: The row is removed from the table immediately.
  3. Check: The table header count decreases by one.
  4. Press the Refresh button (refresh icon) in the toolbar to reload the data from the back end.
  5. Check: The deleted row does not reappear after the refresh, confirming it was successfully deleted in the back end.
